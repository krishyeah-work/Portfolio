01 — The challenge

Simple parts, many combinations.

Every fee is built from the same parts: a flat amount, a percentage, minimum and maximum caps, and sometimes an offer. Which parts apply changes with how the customer pays, the card network, the transaction type and its amount.

Key design challenge

How might a merchant find the fee that applies to them, among dozens of combinations, in seconds?

02 — Context

Money in, money out: two products, one merchant.

Take a florist using QuickBooks. When customers pay for bouquets, QuickBooks Payments charges a fee on each payment. When the florist pays suppliers for flowers, Bill Pay charges a fee on each bill.

03 — Requirements

From pricing tool to table.

Fees are set in Intuit's pricing tool, where each charge is a row of parameters. Not every parameter applies to every charge, so the table had to show only what matters, and keep working when new parameters arrive.

Constraint

Every table had to fit Intuit's standard modal.

The rate table opens in a modal 752 pixels wide. Each extra column squeezes the others and hurts readability, so the number of columns shaped every iteration and decision.

Market review

How payment platforms present their fees.

I reviewed fee pages from Stripe, PayPal, Square, Melio and Bill.com alongside Intuit's existing pop-ups. The review set the row priority and the column order.

Iterations

Four rounds of structure, each within the modal.

V1

Mirror the pricing tool

Every parameter for every charge, laid out as it is set up. Accurate, but very long.

V2

Minimal styling

Lighter type and spacing on the same structure. Easier on the eye, but just as long.

V3

A column grammar

One table per charge type, with the payment method first and the fee last.

V4

Separate columns

Each attribute in its own column, tested with flat and tiered card fees.

Final

Fewer, clearer columns

Network and transaction type share a column, and caps sit under the fee, so four columns fit the modal.

Structure

The method stays first and the fee stays last.

New attributes slot in between. When they no longer fit the modal, related attributes share a column.

Decision 1

Fewer, wider columns, within a 752px modal

Chose
Four columns: payment method, network and transaction type together, transaction range, and the fee last, with caps under the fee.
Over
One column per attribute, or every attribute combined under the payment method.
Why
The standard modal is 752px wide. One column per attribute crowded it and hurt readability, while combining everything hid the structure.
Decision 2

A fixed row order, over the order the data arrives in

Chose
Card payments first, then bank payments, buy now pay later, return charges and other fees.
Over
The order the pricing data returns, which has none.
Why
The order follows how often each fee is looked up and how complex it is, based on the existing pop-ups and benchmarks.
Final design

Four columns in a 752px modal, with icons and collapsible sections.

Sections start open and can be collapsed. Switch products, or see it on mobile, where the table swipes sideways with the payment method pinned.

05 — Reflection

Team, and what I learned.

Team

  • Principal product designerDesign direction and reviews
  • Product managerRequirements and scope
  • EngineeringBuilding the table from pricing data
What I learned

  • Structure is the design

    Column and row order did more for clarity than any styling.

  • Design with the data

    Columns built from attribute names let the table grow without new code.

  • Remove on purpose

    Every column we cut made the right fee faster to find.
